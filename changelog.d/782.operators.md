One release can now serve a root tenant and its child tenants: each entry in the chart's new `tenants:` list runs its own engine with its own workspace volume, event consumer group (`GENUS_EVENT_CONSUMER_GROUP`) and plugin directory on that volume, mounted read-only into the engine (as is the root engine's, when its `ROBOTHOR_PLUGIN_DIR` is on its workspace) so plugins are installed by an install Job that mounts the volume (the chart README has one; list what `.plugins` already holds when upgrading), reads its own provider secret class `engine-providers-<id>`, inherits `engine.env` less any keys it drops (`envOmitPrefixes`, or a key set to `null`), and is reached by the bridge and dashboard through `GENUS_TENANT_ENGINE_URLS` or `GENUS_TENANT_ENGINE_URL_TEMPLATE`, while every signed-in request is bound to its token's tenant under row-level security and a child's engine treats `genus doctor`'s owner check as not applicable, since a child has no owner by design. Turn on switching with `tenancy.switchMode: enforce` (`GENUS_TENANT_SWITCH_MODE`, which refuses unless RLS is genuinely enforcing): a root-tenant owner or admin then acts in a child from the Helm's top-bar picker, a child's admin reaches neither its parent nor a sibling, and the release needs `vaultKey.enabled` with a `vault-key` Vault path (`key` and `fingerprint-salt`) shared by the bridge and every engine — copy an existing `.vault-key` and `.fingerprint-salt` rather than generating new ones, or every stored secret becomes unreadable. The root tenant decides which plugins a child may run with `PUT /api/plugins/{name}/tenants/{tenant_id}` (or Settings › Plugins): a plugin it forces off is refused by that child's engine, even across a restart while grants cannot be read, and one it forces on stays enabled whatever the child's admins choose; `genus tenant set-domains` routes new SSO users by email domain, and `genus tenant move-account` and `genus tenant move-workload` move an account, or a workload's history of runs, steps, schedules, workflow runs and chat sessions, to another tenant in one audited transaction, from the root's shell only and with `--dry-run` first. A deployment can also now roll back to a previous release that carries this rule after a newer one has applied migrations: the older release starts beside migrations numbered strictly above everything it ships and warns which they are, while a gap, a renamed or drifted migration, or a newer row beside one of its own pending migrations is still refused; see [Deployment](deployment.md#running-child-tenants-in-one-release), [rolling back](deployment.md#rolling-back-to-an-older-release), [Plugins](PLUGINS.md#per-tenant) and [Settings](reference/configuration.md).
