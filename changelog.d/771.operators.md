A root-tenant owner or admin can now switch into a descendant tenant and act there, through `POST /api/auth/switch-tenant`; the acting tenant is carried in the access token, never in a header, and a child tenant's admin can reach neither its parent nor a sibling. It is off until you set `GENUS_TENANT_SWITCH_MODE` (`observe` logs what it would do, `enforce` issues tokens), and `enforce` refuses unless row-level security is genuinely enforcing — the same check federation uses. With RLS on, the bridge now binds every signed-in request to its token's tenant, and sign-ins find accounts in any tenant. See [Configuration](configuration.md) for the routes and [Settings](reference/configuration.md) for the two new settings.

A root-tenant owner or admin can now switch tenants from the Helm's top bar: pick a descendant tenant and every page shows that tenant's data from that tenant's engine, under an "Acting as … — Switch back" banner. Anyone with only one tenant never sees the picker, and the switch stays refused until the server sets `GENUS_TENANT_SWITCH_MODE=enforce`. Per-tenant engines are found through `GENUS_TENANT_ENGINE_URLS` or `GENUS_TENANT_ENGINE_URL_TEMPLATE`. See [Deployment](deployment.md#acting-in-another-tenant-from-the-helm).

Several engines, one per tenant, can now share one Redis: give each child engine its own consumer group with `GENUS_EVENT_CONSUMER_GROUP` (for example `engine-<tenant>`), while the root engine keeps the default `engine` and the stream positions it already holds. Every published event now names its tenant and an engine acts only on its own tenant's events, with untagged events still going to the root engine. Only a root tenant reads the root group, so a child engine left on it logs an error and reads nothing until you set its group. See [Event Bus](event-bus.md#one-engine-per-tenant).

One Helm release can now run an engine per child tenant: each entry in the chart's new `tenants:` list gets its own engine, Service and workspace volume, which the bridge and dashboard can reach (see [Deployment](deployment.md) for where the list belongs). Tenants require the new `vaultKey.enabled` and a `vault-key` Vault path holding a base64 `key` and `fingerprint-salt`, so the bridge and every engine share one vault key; on a release that already has a `.vault-key`, copy that key and its `.fingerprint-salt` into Vault rather than generating new ones, because a new key makes every stored secret unreadable ([the chart README](https://github.com/Ironsail-llc/genus-os/blob/main/helm/genus-os/README.md#tenant-cells) shows how). The root engine now sets both tenant variables from the new `global.rootTenant`, whose default of `default` changes nothing. If your `engine.env` sets `ROBOTHOR_TENANT_ID` or `ROBOTHOR_DEFAULT_TENANT` to anything else, move that value to `global.rootTenant`, or the chart will refuse to render.

A tenant can now claim email domains with `genus tenant set-domains acme-child-a example.com`, and a new SSO user from a claimed domain is provisioned into that tenant rather than the default one.
`genus tenant move-account --email alice@example.com --to acme-child-a` moves an existing account and every row linked to it in one transaction, revokes its sessions and audits the move; run it with `--dry-run` first.
If the account's CRM contact has history in its current tenant the move is refused with the counts, and `--detach-person` leaves that contact where it is and gives the account a new one.
See the [CLI reference](reference/cli.md) for every flag; the tenant hierarchy runbook in the repository walks through creating a child tenant end to end.
