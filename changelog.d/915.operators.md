Memory reached through `deep_reason`, the `robothor-memory` MCP server or the orchestrator's `/ingest`, `/stats`, `/query` and `/v1/chat/completions` endpoints is now read and written as the caller's tenant, where before it always went to the default tenant. The orchestrator takes that tenant only from a verified bearer token: on a deployment with more than one active tenant, a request with no token is refused (400), and a bare `X-Tenant-Id` naming a tenant is refused too (401), so a script that posts to the orchestrator needs a token. A single-tenant install behaves as before. See [Tools](TOOLS.md#whose-memory-every-entry-point-acts-as-the-callers-tenant) for where each entry point takes its tenant from.
