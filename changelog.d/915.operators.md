Memory reached through `deep_reason`, the `robothor-memory` MCP server or the orchestrator's `/ingest`, `/stats`, `/query` and `/v1/chat/completions` endpoints is now read and written as the caller's tenant, where before it always went to the default tenant. The orchestrator takes that tenant only from a verified bearer token, applies the bridge's scope and session checks to it, and on a deployment with more than one active tenant refuses a tokenless request, so an OpenAI-compatible client needs a token as its API key there and `scripts/thermal-shed.sh` thermal events no longer reach memory. A single-tenant install behaves as before, including a client that sends a placeholder API key. See [Tools](TOOLS.md#whose-memory-every-entry-point-acts-as-the-callers-tenant) for where each entry point takes its tenant from.
